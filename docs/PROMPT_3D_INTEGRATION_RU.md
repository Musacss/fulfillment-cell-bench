# Промпт: подключить готовую 3D-сцену к Robotization Bench

Ты — разработчик визуального слоя Robotization Bench. У пользователя уже есть готовое 3D-окружение. Твоя задача — подключить к нему существующий симулятор, чтобы сцена достоверно показывала исполнение планов и сравнение результатов. Реализуй интеграцию в доступном проекте, проверь её и объясни запуск. Не ограничивайся планом работы.

Описание ниже сверено с реализацией v1, коммит 1af71b6. Репозиторий ядра: https://github.com/Musacss/fulfillment-cell-bench (приватный; нужен доступ). Сначала проверь текущие файлы: если код изменился, явно перечисли несовпадения. Не превращай этот документ в основание для независимого изменения производственных правил.

## 1. Сначала осмотри сцену и согласуй границу

1. Прочитай AGENTS.md, инструкции проекта, структуру и команды запуска. Определи фактическую технологию сцены: Blender, Unity, Godot, Three.js или другую. Не выбирай другую технологию только ради удобства.
2. Найди имеющиеся модели, анимации, рабочие зоны и интерфейс. Сохрани работу пользователя. Если это Blender-сцена, сначала выясни, предназначена ли она для покадрового воспроизведения в Blender или служит источником моделей для другого приложения. Не предполагай, что файл .blend уже является интерактивным приложением.
3. Прочитай в ядре:
   - docs/SPEC.md и docs/CONTRACTS.md;
   - data/world_spec.json;
   - src/robotization_bench/contracts.py;
   - engine.py, scenarios.py, validation.py;
   - economics.py, grading.py, episode.py;
   - reporting.py и cli.py;
   - tests/test_clock.py и tests/test_invariants.py.
4. Составь соответствие объектов сцены логическим зонам, людям и роботу. Если имена объектов неизвестны, осмотри сцену, а не придумывай, что объекты уже существуют.
5. Ядро рассчитывает производственный результат; сцена воспроизводит его. Геометрия, частота кадров, коллизии и скорость графического проигрывателя не меняют сроки, затраты, очереди или награду.
6. Не меняй общие контракты, движок, генератор дней, цены, случайность и функцию награды ради красивого движения. При невозможности точно отобразить данные назови конкретный пробел и предложи отдельное расширение контракта.

## 2. Что существует сейчас и что предстоит написать

Уже существует Python-движок пакетного расчёта смены и журнал Event. Готового HTTP/WebSocket API, потокового шага simulate.step(), пространственных координат, сервера браузерного интерфейса и универсального снимка состояния сцены сейчас нет.

Для MVP используй воспроизведение уже рассчитанной смены: план → расчёт смены → журнал событий и итог → 3D-проигрыватель. При изменении плана рассчитай новый независимый прогон и начни его с нуля. Ползунок времени, пауза и изменение скорости управляют просмотром, а не производством.

Если сцена не умеет запускать Python, подготовь данные заранее в Python и загружай их в сцену. Если технологически нужен локальный мост, реализуй его явно как новый тонкий слой. Не объявляй несуществующий сервер работающим. Не передавай API-ключи, скрытые проверочные дни и файлы доверенного оценщика в клиентскую сцену.

## 3. Существующие функции, с которыми взаимодействует интеграция

|Функция|Что принимает и возвращает|Применение для 3D|
|---|---|---|
|contracts.load_world()|Возвращает каталог World из data/world_spec.json|Часы, длительности, ёмкости, цены, пороги|
|validation.decode_plan(text, world)|JSON-текст → неизменяемый Plan; InvalidPlan при ошибке|Проверить загруженный или собранный в UI план|
|validation.parse_plan(value, world)|Декодированный JSON-объект → Plan|Проверить данные формы; workers здесь массивы list|
|scenarios.generate(world, seed)|Целый seed → Scenario с отсортированными Order|Получить виды, поступления и сроки заказов|
|engine.simulate(world, plan, scenario, trace=True)|Полная смена → RawReport с events|Главный источник событий для сцены|
|economics.calculate(world, plan, raw)|Доверенные данные → Economy|Итоговая карточка расходов этой смены|
|reporting.export_events(raw, Path)|Пишет Event по одному JSON на строку|Перенести журнал в 3D-приложение|
|grading.evaluate(world, value, scenarios)|JSON-план и набор дней → Evaluation|Допустимость, победа и награда на всём указанном наборе|
|reporting.compare(evaluations)|Словарь Evaluation → Markdown|Готовый текст сравнения; для графиков лучше использовать сами метрики|
|Episode(world, history)|Создаёт открытый исследовательский эпизод|Нужен при отображении действий агента; не требуется для простого просмотра смены|
|episode.observe()|Правила, мир, публичная история и ручной план|Экран изучения предприятия агентом|
|episode.pilot(value, seed, trace=True)|План + публичный день → JSON {raw, economy}|Показать конкретное официальное испытание агента|
|episode.submit(value)|Закрывает эпизод; возвращает {terminal:true, plan:...} либо plan:null|Экран сдачи, но не подтверждение победы|
|episode.stop()|Закрывает эпизод без плана|Отказ от сдачи; не команда остановки производства|

Все эти функции внутри пакета robotization_bench. После submit/stop новые действия Episode вызывают EpisodeClosed. Ошибочный пилот оставляет эпизод открытым и записывается в журнал. simulate сам по себе не изменяет состояние Episode. reference.solve ищет план и не нужен для покадровой анимации.

В raw.events ничего нет при trace=False. episode.log не сохраняет подробные события пилота: для сцены сохраняй именно ответ pilot(trace=True) или отдельный экспорт. results.json из scripts/run_bench.py содержит отчёты без подробных трасс. Нельзя обещать восстановить анимацию из одних итоговых счётчиков.

## 4. Минимальный комплект данных для проигрывателя

Одного JSONL с событиями недостаточно: в Event нет kind заказа, его due и самого плана. Передавай одновременно:

- World и его schema_version/world_id;
- Plan;
- Scenario с seed и всеми Order;
- Event[] в исходном порядке либо events.jsonl;
- RawReport этой же смены;
- Economy этой же смены;
- при показе общего результата — отдельный Evaluation с явным перечнем дней, на которых он посчитан.

У Order четыре поля: id, kind, arrival, due. Допустимые kind: regular, fragile, oversize. ID уникален внутри дня; между прогонами одинаковые ID не означают один объект. Используй ключ (runId, order_id), чтобы сравнение двух планов не смешивало коробки.

Можно создать новый формат-обёртку только для проигрывателя: manifest.json с собственным replay_format, world, plan, scenario, raw, economy, events_file. Это предложение для адаптера, а не существующая схема ядра. Не дописывай поля в Event v1. Исходный порядок удобно хранить локальным eventIndex; его не нужно добавлять в файл событий.

Проверяемый способ получить такой комплект из корня Python-проекта:

```sh
uv run --locked --no-dev python - <<'PY'
import json
import sys
from dataclasses import asdict, replace
from pathlib import Path
sys.path.insert(0, str(Path('src').resolve()))
from robotization_bench.contracts import load_world
from robotization_bench.validation import decode_plan
from robotization_bench.scenarios import generate
from robotization_bench.engine import simulate
from robotization_bench.economics import calculate
from robotization_bench.reporting import export_events

world = load_world()
plan = decode_plan(Path('data/plans/candidate.json').read_text(), world)
scenario = generate(world, 11)
raw = simulate(world, plan, scenario, trace=True)
economy = calculate(world, plan, raw)
out = Path('artifacts/3d/candidate-11')
out.mkdir(parents=True, exist_ok=True)
export_events(raw, out / 'events.jsonl')
manifest = {
    'replay_format': 'robotization-bench.replay.v1',
    'world': world,
    'plan': asdict(plan),
    'scenario': asdict(scenario),
    'raw': asdict(replace(raw, events=())),
    'economy': asdict(economy),
    'events_file': 'events.jsonl',
}
(out / 'manifest.json').write_text(json.dumps(manifest, ensure_ascii=False, indent=2))
print(out.resolve())
PY
```

Для ручного процесса заменить candidate.json на manual.json, а каталог — на manual-11. Для другого публичного дня можно использовать 29 или 47. Не сравнивать планы на разных днях. candidate.json — пример с пятью людьми; найденный контрольной стратегией план отдельно лежит в evidence/frozen-v1/submission.json и содержит четыре человека. Не выдавай пример candidate.json за тот план, которому принадлежат опубликованные результаты стратегии.

Есть и короткая существующая CLI-команда:

```sh
PYTHONPATH=src uv run --locked --no-dev python -m robotization_bench.cli pilot --plan data/plans/candidate.json --seed 11 --events artifacts/3d/events.jsonl > artifacts/3d/pilot.json
```

Перед перенаправлением создать artifacts/3d. CLI пишет raw без events и economy в stdout; мир, план и сценарий передаются отдельно. CLI сам разрешает только публичные development_seeds. В защищённом режиме проверочные дни не экспортируются в сцену до разрешённого завершения испытания.

## 5. Пространственная организация готовой сцены

Предусмотри привязки, названия которых выбери по фактической сцене:

- зона 1: подготовка тары, входная очередь;
- зона 2: комплектация, входной буфер;
- зона 3: ручная упаковка, робот-упаковщик, общий входной буфер первой упаковки и отдельная очередь переделки;
- зона 4: контроль и сортировка, входной буфер;
- визуальные области исходов: годные заказы, выданный брак, окончательный брак;
- место отображения перерыва — по желанию, без производственного перехода туда;
- точки появления работников, рабочие позиции, места ожидания коробок и пути переходов.

Ядро не задаёт метров, скорости шага, габаритов лотков или конвейеров. Координаты и траектории — настройки визуального слоя. Их длина не пересчитывает время перехода. Одновременным ручным работникам нужны отдельные визуальные позиции: в мире v1 нет лимита «один ручной стол на зону». Не вводи такой лимит физическими коллизиями сцены.

Первое разрешённое число в plan.workers[i] — начальная зона человека wi. Это не этап, на котором он навсегда закреплён. Другие числа — зоны, где он имеет право работать. Порядок людей в массиве влияет на назначение. При robot=false оборудование можно скрыть или показать выключенным с ясной пометкой «не приобретено». При robot=true и route=manual купленный робот стоит без производственной работы и продолжает участвовать в расходах.

## 6. Часы и порядок событий

Все числа ниже — текущие значения каталога, а не константы для кода сцены. Читай их из World:

- tick_seconds=30;
- shift_ticks=960: обычная смена 480 минут;
- overtime_ticks=120: разрешённая доработка ещё 60 минут;
- горизонт H=1080 тиков, то есть 540 минут;
- walk_ticks=2: переход между любыми двумя разными зонами 60 секунд;
- break_at=440: перерыв запрашивается начиная с 220-й минуты;
- break_length=40: перерыв длится 20 минут;
- jam_service=8: помощь у робота занимает 4 минуты плюс переход, если он нужен.

Время t — относительное от начала смены, а не местное время суток. В интерфейсе «03:40 смены» допустимо, конкретный час начала смены без настройки не придумывай.

На каждом тике движок:
1. Завершает операции людей в порядке w0,w1,…; закончившаяся помощь освобождает помощника.
2. Обрабатывает окончание цикла робота: либо jam, либо finish, в том числе после помощи.
3. Добавляет поступившие заказы по ID.
4. На H заканчивает расчёт, новых назначений нет. Если все заказы уже получили исход, расчёт может закончиться раньше.
5. Свободный робот выбирает заказ.
6. Люди по порядку списка либо уходят на перерыв, либо помогают роботу, либо берут операцию.

Сохраняй порядок строк исходного журнала. Не пересортировывай одинаковый tick по имени события, order_id, resource или алфавиту. События enqueue/start/finish одного тика могут последовательно передавать один заказ между ресурсами. Обрабатывай всю группу одного tick прежде, чем рисовать устойчивое состояние кадра: промежуточное состояние между finish и enqueue не является потерей заказа.

Тики — логическая шкала, кадры — графическая. Для промежуточного времени T в тиках применены все события с tick≤T. Движение интерполируется внутри полуоткрытых интервалов [tick,end_tick). Не запускай следующий заказ по окончании графического клипа: только по журналу.

## 7. Поля Event и полный разбор событий

Все ключи обязательны, неприменимые значения равны null:

```json
{"tick":10,"kind":"start","order_id":7,"resource":"w0","stage":3,"attempt":0,"end_tick":23}
```

Это пример формы, а не обещание такой записи в любом дне. stage=1..4, attempt=0 или 1, resource — w0,w1,…, robot либо null. Время — в тиках.

### arrival

Заказ поступил извне. Создай ровно один объект с order_id, возьми kind/arrival/due из Scenario. Стартовая позиция — зона входа. Сразу вслед за arrival обычно приходит enqueue в stage=1 на том же тике. Не создавай вторую коробку на enqueue.

### enqueue

Помести существующий заказ в очередь указанного stage. Для stage=3, attempt=1 это отдельная очередь переделки. Все остальные — обычные входные очереди соответствующего этапа. Отпускается предыдущая операция; визуально коробка встаёт на свободное фактическое место. Сохранить порядок поступления записей.

### start

Ресурс захватывает заказ и выходное место следующего этапа. Убери заказ из исходной очереди. Для stage=1..3 зарезервируй одно место перед stage+1. Для stage=4 выходной резерв не нужен. При stage=3, attempt=1 изымается заказ из очереди переделки, а не из обычной очереди упаковки.

Человек занят уже с tick, даже если сначала идёт; end_tick включает и переход, и работу. До рассмотрения возможного walk не начинай изображать работу у стола. Робот начинает цикл непосредственно на stage=3, без walk. Предварительный end_tick робота не гарантирует освобождения: на этом тике возможен jam.

### walk

Это начальная часть уже зарегистрированного start или assist того же человека/заказа/тика. Не новая операция, не вторая занятость и не перенос в другую производственную очередь. Ищи родительскую запись и связывай с ней. За промежуток [tick,walk.end_tick) человек движется от прежней зоны к event.stage. После walk.end_tick проигрывает работу до end_tick родительской операции.

Пример: start [10,23), walk [10,12) означает 2 тика перехода и 11 тиков обработки. При отсутствии walk человек уже в нужной зоне. Отдельного события «дошёл» нет.

В ядре заказ изъят из очереди сразу на start, до прихода работника. Честное визуальное решение: коробка в области «назначено/в обработке», человек идёт к ней. Нельзя продолжать считать её ожидающей в буфере, требовать забрать её физически со старого стола или начислять ещё одно время доставки.

### finish

Завершение операции, а не всего заказа. Для stage<4 следом идёт enqueue следующего этапа. Снимай выходной резерв и превращай его в фактическую занятость буфера на enqueue. Можно кратко подсветить выход, но не добавляй транспортное время.

На stage=3 это одна завершённая упаковка: pack_finished+=1, если resource=robot — auto_finished+=1. На stage=4 ожидай того же тика good, escaped, scrap либо enqueue stage=3 attempt=1. Только эти дальнейшие данные определяют исход.

### jam

Цикл робота дошёл до планового конца и застрял. Автоупаковка ещё НЕ завершена. Объект остаётся у robot; его место в выходном буфере stage=4 остаётся зарезервированным. Робот не берёт следующий заказ. Останови рабочую анимацию в безопасной позе, покажи красный/янтарный индикатор и статус «Застрял — нужен работник».

Случайность в сцене не разыгрывается. Если jam не пришёл, самостоятельно останавливать робот нельзя. Отдельное событие defect при jam не появляется: это другая механика.

### assist

Назначен конкретный помощник resource=wi с правом работы в зоне 3. Робот по-прежнему владеет тем же order_id, помощник имеет ссылку на него для обслуживания. Не клонируй коробку и не забирай её в руки помощника как самостоятельный производственный заказ.

С tick до end_tick помощник занят; возможный walk — начальный подинтервал. До его прихода показывай «Помощник идёт», затем «Устранение застревания». Робот всё ещё не работает над новым заказом.

Отдельного finish для человеческого assist НЕТ. Освобождай помощника по assist.end_tick. На этом же тике движок выдаёт finish для robot и enqueue в stage=4. После помощи второй упаковочный цикл не нужен. Человек может получить новый start на том же тике. На временной шкале помощь и следующая работа не перекрываются.

Если горизонт наступил раньше assist.end_tick, обслуживание остаётся незавершённым, заказ один раз входит в unfinished. Если помощника нет, robot может стоять до H. Работник с другой активной операцией не бросает её ради помощи.

### break

Начало перерыва человека, resource=wi; order_id/stage/attempt=null, end_tick задан. Он происходит один раз, как только человек свободен на/после break_at. Занятую работу и walk перерыв не прерывает. При выборе между уже положенным перерывом и помощью сначала перерыв.

На [tick,end_tick) показывай статус отдыха; отдельного события окончания нет. Можно оставить человека у своей последней зоны с ненавязчивым значком отдыха. Если ведёшь его в комнату отдыха, это исключительно декоративная анимация внутри готового интервала: не меняй логическую зону, не добавляй переход туда/обратно к производственному времени.

### good

Контроль закончен: годный заказ. Увеличь good и помести объект в область готовых заказов. Если tick≤due — также on_time. В противном случае покажи «Годен, опоздал»: это выполненный заказ со штрафом, не scrap. Не прибавляй good на finish упаковки.

### escaped

Контроль пропустил дефект: заказ физически выдан, но не считается good и on_time. Это отдельный конечный исход с отдельным штрафом. В режиме объяснения можно показать «Выдан брак». В реалистичном производственном виде оператор его не обнаружил — поэтому не изображай успешное обнаружение контролёром; истинный исход допускается раскрыть в аналитике после выдачи.

### scrap

Дефект обнаружен после второй упаковки. Это окончательный брак, без третьей попытки. Помести заказ в область списания. Он больше не участвует в очередях, не становится good и отдельно не считается unfinished.

## 8. Очереди: вид, ёмкость, резервы и движение

Логические очереди:

|Очередь|Назначение|Ёмкость v1|Показывать|
|---|---|---|---|
|Q1|Ожидание подготовки|Не ограничена|Входящую пачку/стеллаж и точный счётчик|
|Q2|Ожидание комплектации|12|12 слотов, ожидающих отдельно от резервов|
|Q3|Первая упаковка|10|10 слотов; поток к роботу и ручной упаковке общий до выбора|
|Q4|Ожидание контроля|8|8 слотов, отдельные фактические места и резервы|
|R|Повторная упаковка|Не ограничена|Отдельный помеченный стеллаж; не часть 10 мест Q3|

Для каждого ограниченного буфера всегда:

    waiting + reserved ≤ capacity

Показывай три числа: «ждут», «зарезервировано», «ёмкость». Фактическая коробка занимает заполненный слот. Зарезервированное место — контур/полупрозрачный маркер, привязанный к ID заказа. Это НЕ вторая физическая коробка. Место заранее удерживается производящей операцией.

Обновления:
- start на stage1: убрать из Q1, reserved(Q2)++;
- start на stage2: убрать из Q2, reserved(Q3)++;
- start на stage3 attempt0: убрать из Q3, reserved(Q4)++;
- start на stage3 attempt1: убрать из R, reserved(Q4)++;
- start на stage4: убрать из Q4, нового резерва нет;
- finish на stage1/2/3: reserved соответствующего выхода--; следующий enqueue добавляет фактическое waiting;
- jam/assist не освобождают выходного резерва робота;
- конец просмотра/горизонт не превращает резервы в готовые коробки.

Слоты Q2/Q3/Q4 освобождаются уже при start следующего этапа, а не после finish этого этапа. При переделке из контроля место Q4 уже было освобождено ранее на start контроля.

Если буфер заполнен коробками и резервами, предыдущий этап не может взять новую работу. Не показывай «операция закончена, но выхода нет»: выход был гарантирован до старта. Уже начатая операция не отменяется. Не назначенный работник может простаивать из-за полного выхода — это исправное поведение.

Очередь выбирает первый ПОДХОДЯЩИЙ заказ. Неподходящий для робота fragile/oversize не блокирует regular позади него. Поэтому в bypass робот может выбрать не самую левую коробку Q3. Остальные сдвигаются визуально, но порядок логических записей не меняется. Не создавай независимые производственные FIFO-очереди к роботу и человеку: в ядре Q3 одна.

Для больших неограниченных очередей можно рисовать первые N коробок и «ещё K». Все ID и порядок сохраняются в состоянии, объекты по требованию переиспользуются. Предел числа видимых моделей не ограничивает производство.

## 9. Как выбираются работники и маршруты

Свободный человек рассматривается в порядке массива workers. Его приоритет: положенный перерыв, помощь застрявшему роботу при разрешённой зоне 3, затем этапы 4→3→2→1 среди разрешённых. Для ручной упаковки сначала R, потом подходящие Q3. При невозможности зарезервировать выход он может рассмотреть другой разрешённый этап.

Робот получает право выбора раньше людей этого тика. На роботе одна упаковка одновременно. Ручных операций в зоне 3 может быть несколько — по числу назначенных людей. Робот не роботизирует этапы 1,2,4.

Маршруты:
- manual: все упаковки ручные, даже если робот куплен;
- all: все виды идут к роботу при attempt0;
- bypass: только regular attempt0 идёт к роботу; fragile и oversize упаковуются вручную;
- любая attempt1 всегда ручная.

Если robot=false, допустим только route=manual. Если в all нет пригодного работника для помощи или переделки, такой заказ может остановить поток/остаться незавершённым. Сцена не должна «спасать» план дополнительным невидимым человеком или самостоятельно переключать маршрут после jam.

trays=true означает использование стандартных лотков при первой начатой упаковке ЛЮБОГО вида заказа, включая ручной обход. Лотки могут покупаться без робота. Заказ списывает один лоток на первую упаковку; переделка не списывает второй. Каталог не моделирует возврат, складской запас или физическую циркуляцию лотков: не добавляй такие ограничения. Видимый лоток — иллюстрация параметра стандартизации.

|Вид|Подготовка|Комплектация|Упаковка|Контроль|
|---|---|---|---|---|
|regular|3 (1,5)|5 (2,5)|11 (5,5)|3 (1,5)|
|fragile|4 (2)|7 (3,5)|14 (7)|4 (2)|
|oversize|5 (2,5)|9 (4,5)|17 (8,5)|5 (2,5)|

Автоупаковка: bare — 6/10/14 тиков по порядку regular/fragile/oversize; tray — 3/8/12. Ручная переделка длится как ручная упаковка соответствующего вида. Фактические начала/окончания берутся из событий. Таблицы нужны для объяснения и проверки, не для самостоятельного назначения работы сценой.

Ядро использует стабильные ключи (seed,order_id,stage,attempt,event_type), SHA-256 и отдельные события jam/defect/detect. Их воспроизведение не зависит от FPS и соседних заказов. Для внешнего вида можно выбрать декоративную фазу движения, но она не меняет производственные исходы.

## 11. Переделка и скрытое качество

При завершении упаковки ядро определяет defect, но отдельного события «появился дефект» в журнале нет. Обнаружение происходит после контроля. Не считай любую коробку с attempt1 отдельным новым заказом.

Три случая после finish stage4 attempt0:
1. good — сразу готов;
2. escaped — сразу выдан брак, попыток больше нет;
3. enqueue stage3 attempt1 — обнаружен дефект, тот же ID отправлен в R.

После R человек вручную упаковывает заказ, затем он снова проходит stage4. Подготовка и комплектация повторно не выполняются. После второй проверки возможны good, escaped или scrap. attempt2 запрещена.

Поскольку нет отдельного detected/rework_requested, вывод «обнаружен дефект» делается по переходу finish(4,0)→enqueue(3,1) одного order_id. Само событие finish контроля содержит старую attempt=0, а следующий enqueue — новую attempt=1. Храни номер попытки для текущей операции, не переписывай ретроспективно старые интервалы.

До контроля не рисуй красную «известно бракованную» коробку по сведениям из будущих строк. Для публичного просмотра полную трассу можно загрузить заранее, но состояние в момент t использует только её префикс. Отдельно разрешён явный аналитический режим с раскрытием исходов после завершения.

## 12. Как должны выглядеть состояния

Работник: ожидание в последней зоне; переход; подготовка/комплектация/упаковка/контроль; движение к роботу; помощь; перерыв. После перерыва и помощи свободен по end_tick. После обычной работы — по finish. Перемещения человека из zone3 в zone4 и обратно включаются в существующие start/walk; не добавляй их повторно.

Робот: не приобретён; куплен и выключен маршрутом; свободен; упаковка; застрял и ждёт; помощник идёт; обслуживание; упаковка завершена. После помощи он сразу освобождается, а не «возобновляет цикл на остаток времени». После jam шкала цикла должна смениться на неопределённое ожидание; не продолжай прогресс сверх 100% и не выдавай готовый заказ до finish.

Заказ: ещё не поступил; ожидает Q1/Q2/Q3/Q4/R; назначен/обрабатывается; good; escaped; scrap. unfinished — итоговый признак на H для всех неокончивших заказов, а не событие из журнала. Просроченность — отдельная метка, не состояние очереди. Терминальные good/escaped/scrap взаимоисключающие.

Рекомендуемые визуальные различия: regular — стандартная коробка; fragile — отчётливый значок хрупкости; oversize — увеличенный габарит. Цвета дополнить текстом/значками. Для резервов использовать контур, для ожидания — статичную коробку, для активного заказа — подсветку рабочего места, для jam — предупреждение. Не полагаться на один цвет.

## 13. Горизонт и конец воспроизведения

Не генерировать производственные события после H. Операция с end_tick>H остаётся незавершённой; обрезать анимацию на H, не дорисовывать finish. На самом H существующие завершения допустимы, новые start/assist/break уже не выдаются. Полуоткрытость интервалов обеспечивает точное переключение на их границах.

Движок может закончить расчёт раньше H, если все заказы получили конечный исход. В Event нет shift_end, horizon или done. Последняя строка журнала также может находиться значительно раньше H при безвыходном простое. Поэтому не считать «последнее событие = конец смены» универсальным правилом.

Для MVP длительность просмотра можно фиксировать H и после последнего события показывать остаточный простой. Допустимо остановить просмотр раньше, когда все Scenario.orders получили good/escaped/scrap; подписать «Все заказы обработаны». Не получать окончание только как max(end_tick): в журнале есть интервалы, уходящие за H.

В конце проверить:

    total = good + escaped + scrap + unfinished

В unfinished входят все очереди, R, активные человеческие заказы и заказ в роботе, включая застрявший. Помощник не добавляет ещё одну незавершённую коробку. Непоступившие на выбранном промежуточном кадре заказы — «ещё не поступили», а не производственные unfinished на конец смены.

Пауза и закрытие окна проигрывателя не равны Episode.stop(). Кнопка «Сбросить просмотр» тоже не сдаёт пустой план. Разведи элементы управления анимацией и действия агента.

## 14. Показатели и экономическая панель

Показывай ход смены: текущее время; поступило/ещё ожидается по сценарию; good и on_time; escaped и scrap; текущие заказы в системе; очереди и резервы; занятость людей и робота; завершённые упаковки и их автоматическую часть. Если показываешь долю авто: auto_finished/pack_finished; при нуле знаменателя — 0 либо «ещё нет упаковок». Знаменатель включает повторные ручные упаковки. Покупка робота не означает 100% автоматизации.

Итоги брать из RawReport и Economy. labor_ticks — человеко-тики, а не длительность смены. Перевод: labor_hours=labor_ticks*tick_seconds/3600. Деньги — целые евроценты, вывод euros=cents/100. Не заменяй внутренний расчёт округлёнными значениями экрана.

В Economy purchase — разовая инвестиция для сравнения с бюджетом, total — расходы дня. Не складывай их повторно. costs содержит:
- depreciation: списание покупок на 500 смен, округление половины цента вверх;
- service: обслуживание купленного робота;
- shifts: полные оплаченные смены всех работников;
- overtime: оплачиваемые тики сверх смены;
- trays: использованные лотки;
- materials: каждая начатая упаковка, включая переделку;
- rework: доплата за фактически начатую повторную упаковку;
- late: good−on_time;
- unfulfilled: scrap+unfinished;
- escaped: отдельный штраф выданного брака.

Справочные текущие цены: покупка robot=13 500 €, trays=1 800 €, бюджет=18 000 €; смена человека=152 €, обслуживание робота=7 €/день; сверхурочный тик=0,25 €/человек; материал упаковки=0,12 €; лоток=0,06 €; переделка=0,70 €; поздний good=3,20 €; scrap/unfinished=35 €; escaped=65 €. Читать из World, не дублировать константами.

Активный труд включает обработку, переходы и помощь, но не ожидание и отдых. Оплата целой смены сохраняется даже у простаивающего человека. Помощь роботу не создаёт вторую зарплату. Сверхурочная доплата считается от конца обычной смены до последнего занятого тика человека, включая промежуточное ожидание, а не только по длительности активных операций после смены.

Важная особенность: RawReport уже содержит итог за всю смену. Нельзя выдавать его заранее рассчитанные labor_ticks/overtime_ticks за текущие на первом кадре. Для промежуточного активного труда суммировать пересечения человеческих start/assist с [0,currentTick), не суммируя walk вторично. Перерывы исключить. Для промежуточных overtime брать последнее уже наступившее занятое время сверх shift_ticks. Полную конечную стоимость выводить как «Итог рассчитанной смены» либо только в конце; начислять штраф за unfinished до H нельзя. Отдельной потоковой функции экономики в ядре нет.

Evaluation — результат НАБОРА дней. Не присваивай его одной показанной смене и не генерируй награду из красивой анимации. valid=корректная структура, feasible=выполнены эксплуатационные ограничения, win=также снижены затраты и труд и достигнута доля автоматизации. Это три разных признака.

Пороги: good/total≥94% в каждый день; on_time/total≥90% по сумме; escaped/total≤1% в каждый день; покупка в бюджете. Для win дополнительно C<C_base, labor<labor_base и auto≥25%. Отображай причины отказа. Награда хранится как reward_num/reward_den, сравнение выполняет ядро. В UI дробь можно округлить только для показа.

## 15. Функции, которые нужно реализовать в визуальном адаптере

Имена ниже ПРЕДЛАГАЕМЫЕ. Это не готовые функции существующего ядра. Адаптируй к языку сцены, сохрани смысл и отделение расчёта от графики:

|Функция адаптера|Ответственность|
|---|---|
|loadReplay(manifest, events)|Проверить версии, мир, план, ссылки на ID; загрузить неизменяемый исходный прогон|
|bindScene(mapping)|Связать зоны/слоты/ресурсы с существующими объектами; выдать понятные ошибки отсутствующих привязок|
|resetReplay()|Обнулить время, очереди, резервы, состояния и графические объекты прошлого прогона|
|applyEvent(state, event, eventIndex)|Изменить только логическое состояние по правилам выше; без назначения новых работ|
|advanceTo(tick)|Применить неприменённый префикс журнала по порядку, закрыть истёкшие assist/break; не зависеть от FPS|
|seekTo(tick)|Восстановить то же состояние после прыжка назад/вперёд через сброс и повтор либо проверенные снимки|
|sampleVisuals(tick)|Вычислить положения и фазы анимации по активным интервалам; не менять результаты|
|renderQueues(state)|Показать waiting/reserved/overflow для каждого отдельного буфера|
|renderResources(state,tick)|Состояния людей, право зон, ходьбу, работу, перерывы и jam/assist робота|
|renderOrders(state,tick)|Один объект на ID; вид, попытку, срок, исход и положение|
|renderMetrics(state,tick)|Текущие счётчики отдельно от окончательных RawReport/Economy/Evaluation|
|setPlaybackSpeed(multiplier)|Менять визуальную скорость, не данные и не производственный seed|
|loadComparison(left,right)|Два независимых состояния с общим seed/потоком заказов и синхронизированной шкалой времени|
|disposeReplay()|Остановить клипы, убрать подписки/таймеры и освободить объекты старого прогона|

Сначала можно восстанавливать состояние с нуля на каждый seek: в смене немного заказов. Снимки состояния для ускорения — локальная оптимизация адаптера; их формат версионируй отдельно. Не называй их существующим snapshot API движка.

Состояние адаптера должно знать как минимум: orderById, очереди Q1..Q4/R, владельцев выходных резервов, активные человеческие операции, связь assist→robot, местоположение людей, интервалы break/walk, режим robot, исходы заказов, позицию чтения событий. Рабочие ресурсы и сущности заказов — разные таблицы.

При обработке человеческого start/assist найди его walk того же тика заранее внутри группы; иначе после seek первая часть операции может ошибочно выглядеть как работа у стола. Перед событиями нового тика закрой истёкшие интервалы отдыха и помощи, но не освобождай обычную операцию только по её предсказанному end_tick: её finish должен быть в корректной трассе, иначе это ошибка входа. Предсказанный end_tick робота никогда не освобождает robot без finish/jam.

Нельзя привязывать таймеры производства к событиям анимационных клипов или физического столкновения. Не использовать «один setTimeout на событие» как единственный источник истины: перемотка и скорость потребуют вычисления состояния по логическому времени. Весь кадр должен восстанавливаться по (исходные данные, tick).

## 16. Ручные эталоны, на которых сверить анимацию

### Один заказ, один универсальный человек

Тестовый мир: один regular id=7, arrival=0, due=28, дефект ручного regular принудительно отключён в отдельной тестовой копии World. План workers=[[1,2,3,4]], robot=false, trays=false, route=manual. shift_ticks=20, overtime_ticks=8. Эти настройки — тест, не изменение публичного мира.

|Интервал|Действие|
|---|---|
|[0,3)|Подготовка в зоне 1|
|[3,5)|Переход 1→2|
|[5,10)|Комплектация|
|[10,12)|Переход 2→3|
|[12,23)|Упаковка|
|[23,25)|Переход 3→4|
|[25,28)|Контроль|
|tick=28|good, on_time|

На H=28 заказ завершён; на H=27 остаётся в контроле и считается unfinished. Все переходы уже включены в start.end_tick. Два regular с arrival=0 в таком же мире при достаточном горизонте завершаются на 28 и 58 из-за приоритета последующих этапов и обратного перехода человека.

### Застревание, отложенная помощь и перерыв

Отдельный тестовый World: shift=12, break_at=12, break_length=5, jam regular с лотками=100%, defect auto regular с лотками=0; plan robot=true,trays=true,route=all,workers=[[1,2,3,4]]. Один regular arrival=0,due=32.

- [0,3) подготовка; [3,5) переход; [5,10) комплектация.
- tick10 робот берёт заказ; человек в зоне2. Робот резервирует место Q4.
- [10,13) автоупаковка; tick13 jam. Заказ остаётся у робота.
- Человек ушёл на перерыв [12,17), поэтому не помогает на tick13.
- tick17 assist.end_tick=27; walk [17,19) из зоны2 в3; помощь [19,27).
- tick27 finish(robot), enqueue Q4, затем человек получает контроль с переходом [27,29).
- [29,32) контроль; tick32 good.
- При H=22 помощь ещё идёт; заказ unfinished один раз. При H=27 упаковка завершена, но контроль не стартует, потому что новые назначения на H запрещены.

Вся последовательность уже представлена в tests/test_invariants.py. Не выставляй обязательный jam в обычных демонстрационных данных: это только управляемая проверка визуального адаптера.

## 17. Проверки и критерии готовности

Реализуй содержательные проверки адаптера, а затем покажи сцену:

1. Один заказ и границы 27/28 тиков совпадают с эталоном.
2. Один order_id не создаёт две коробки; все заказы имеют ровно одно логическое положение/исход. Связь помощника с заказом не является вторым владением.
3. В каждом Q2/Q3/Q4 сумма waiting+reserved не превышает ёмкость; R считается отдельно.
4. При jam сохраняются robot, коробка и резерв Q4; помощник сначала идёт и только затем обслуживает.
5. После assist нет ожидания несуществующего человеческого finish; робот не начинает второй упаковочный цикл.
6. В bypass сложные заказы идут вручную, а regular позади них может быть взят роботом. В all ручной упаковщик не перехватывает attempt0.
7. Переделка того же ID проходит R→ручная упаковка→контроль; третьей попытки нет.
8. Перерыв не прерывает начатую работу, завершение перерыва не требует отдельного события.
9. Состояние после seekTo(t) равно обычному воспроизведению до t. Проверить forward/backward, jam, активный walk и конец перерыва.
10. Пауза, скорость 1×/20×/100× и пропуск кадров не меняют конечные счётчики и распределение заказов.
11. На H незавершённая работа не «доигрывается» в пользу результата. Отсутствие последних событий не завершает смену преждевременно.
12. Конечные good/on_time/escaped/scrap/unfinished, pack_started/pack_finished/auto_finished, trays_used/rework_started совпадают с RawReport. active labor совпадает после обрезания интервалов по H.
13. Все расходы совпадают с Economy; purchase показывается отдельно. Результат набора дней не подписан как результат одного дня.
14. Перезапуск и переключение плана очищают старые объекты, подписки и счётчики. Одновременное сравнение не смешивает ID.
15. Неизвестный kind события, неподдерживаемая версия, отсутствующий заказ/ресурс, убывание tick, нарушенная последовательность или повторное конечное событие дают явную ошибку с номером строки. Отсутствие привязки сцены объясняется названием зоны/объекта. Не игнорируй неизвестные события молча.

Различай ошибку файла и законный плохой план: пустая нужная зона, постоянный простой, незавершённые заказы и застрявший навсегда робот могут быть правильным результатом расчёта. Проверки не должны автоматически «чинить» такой прогон.

Не проверяй анимацию только скриншотом начального состояния. Нужны моменты заполненного буфера, резервов, помощи роботу, ручного обхода, переделки и итогового отчёта. Если в обычном seed редкий случай не встретился, используй отдельную помеченную тестовую трассу, не выдавая её за результат публичного мира.
